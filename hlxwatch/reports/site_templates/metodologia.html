Metodologia

In breve

HLX Watch sorveglia dati pubblici dei giochi Valve su Source 2 e registra ogni riga che contiene riferimenti a HLX (il presunto nome in codice di Half-Life 3) o ad altri progetti non annunciati. Ogni voce porta alla sua fonte: il commit di SteamTracking da cui proviene, il file e la riga. Lo strumento non usa account, depot privati né scraping di siti terzi, e non interpreta i dati da solo: le interpretazioni stanno solo nell'analisi AI, separate dai fatti.

Questa pagina è generata dalla stessa configurazione che usa lo strumento, quindi pesi e soglie qui sotto sono quelli realmente applicati. Aggiornata {{ generated }}.

I repository SteamTracking contengono file estratti dai giochi e dump generati da strumenti (stringhe dei binari, schemi del motore, ConVar). HLX Watch è quindi una fonte secondaria: dipende da come SteamTracking estrae i dati, e un cambio di formato dei dump può far "comparire" o "sparire" righe che Valve non ha toccato.

Come vengono trovate le voci

  1. Monitoraggio dei commit. Per ogni commit nuovo lo strumento legge la patch di ogni file; se GitHub non la fornisce (file troppo grandi) scarica le due versioni e le confronta. Le righe aggiunte, rimosse o modificate che contengono una parola chiave diventano voci. Limite: l'API di GitHub espone al massimo 3000 file per commit.
  2. Scansione completa (ogni {{ full_scan.interval_hours }} ore). L'ultima versione di ogni repository viene scaricata senza storia e cercata per intero, compresi i file che la ricerca di GitHub non indicizza e quelli tagliati dal limite dei 3000 file. Prefiltro: {{ full_scan.prefilter }}; soglia {{ full_scan.min_score }} punti.
  3. Prima comparsa. Per le voci trovate dalla scansione completa, lo strumento ripercorre la storia del file e cerca per bisezione il primo commit in cui la riga compare.
  4. Steam. Nuove build per branch e app nuove con developer/publisher Valve, nome sospetto o parole chiave.
  5. Struttura dei repository. A ogni run si confrontano gli elenchi delle cartelle sotto game/ e dei file in manifests/ (un file per depot Steam) di ogni gioco, e delle cartelle del repository dei Protobuf (un protocollo di rete per gioco): una voce che prima non c'era diventa una voce structure da {{ structure_score }} punti, anche se nessun file scrive il nome del progetto. Lo stesso per i dump delle DLL in game/bin/win64 e nella cartella del gioco: una DLL nuova è un sottosistema nuovo.
  6. Entità senza padrone. Le definizioni delle entità per l'editor (game/core/*.fgd) arrivano in ogni gioco; le classi C++ che le implementano solo nel gioco che le usa. Alla scansione completa giornaliera si confrontano tutti i giochi insieme: un'entità che nessun gioco implementa, o un helper di Hammer mai visto, appartiene a un altro progetto. Hammer stesso fa questo controllo. Le FGD condivise dei nemici sono anche file sorvegliati: CS2 e Dota 2 non hanno nemici, ma quei file cambiano proprio nelle date delle tracce HLX.
  7. Famiglie di token di localizzazione. Ogni testo a schermo è un token "Famiglia_Nome" nei file *_english.txt (CSGO_, DOTA_, Citadel_, HLVR_): è il posto in cui Valve è obbligata a scrivere il nome del progetto. Le famiglie presenti vengono imparate alla prima scansione completa; poi un file di localizzazione nuovo vale {{ loc.score_new_file }} punti e una famiglia mai vista con almeno {{ loc.min_tokens }} testi in un commit {{ loc.score_new_prefix }} (Deadlock meno: ogni eroe nuovo porta la sua famiglia).

Nomi di progetto nuovi e file sorvegliati

Le parole chiave trovano solo nomi già noti. Per accorgersi di un progetto con un nome diverso, HLX Watch guarda i posti in cui Valve scrive i nomi in codice: le espressioni mod != nome degli strumenti, prodotti e componenti del bug reporter, le cartelle source2/main/content/nome e i rami di compilazione che restano nei binari (C:\buildworker\csgo_rel_win64\...: il ramo che ha prodotto la DLL). Un nome che non è tra quelli noti diventa una voce "codename" da {{ codename_score }} punti. Nomi noti finora: {{ project_names|join(", ") }}.

Filtri contro i falsi positivi

  • Righe che contengono {{ global_excludes|join(', ') }} (nome in codice di Deadlock) scartate, salvo match ad alta rilevanza.
  • Corrispondenze con maiuscole miste (hLX, HLx): sequenze casuali nei dump binari, scartate.
  • Frammenti binari: righe con poche lettere o piene di simboli e sequenze di escape, scartate sotto i {{ severity.high }} punti.
  • Le regole correnti vengono riapplicate a tutto l'archivio a ogni run: una modifica alle regole pulisce anche lo storico.

  • Data modifica: data del commit di SteamTracking, cioè di quando il dato è cambiato nei file del gioco. Vista il: quando lo strumento l'ha registrata (diversa per l'archivio storico).
  • Prima comparsa: primo commit in cui la riga compare nel file. "Almeno dal": la riga c'era già quando SteamTracking ha iniziato a tracciare quel file, quindi può essere più vecchia.
  • Nuova: la stringa (o il suo identificatore) non era mai stata vista prima nell'archivio.
  • + altri N file: la stessa riga è cambiata in più file dello stesso commit (tipico dei dump di più eseguibili): conta come un'unica modifica. + altre N righe nello stesso file: la stessa stringa compare in più punti dello stesso file (per esempio una classe ripetuta nel dump di un eseguibile).
  • Data delle voci della scansione completa: quando la prima comparsa è nota, la data della modifica è quella del primo commit in cui la riga compare, non quella della scansione che l'ha trovata.

Limiti noti

  • Ritardo: i run sono pianificati ogni 30 minuti, ma GitHub li avvia in modo irregolare; una scoperta può arrivare con ore di ritardo rispetto al commit.
  • Parole chiave: si trova solo ciò che corrisponde all'elenco qui sopra. Un progetto con un nome in codice nuovo passa inosservato finché non viene aggiunto.
  • Formato dei dump: SteamTracking cambia talvolta come estrae i dati (per esempio dal 13 ottobre 2026 molte stringhe già note sono filtrate dai dump dei binari). Spostamenti tra file non sono modifiche di Valve.
  • Codice condiviso: Source 2 è un motore comune; la stessa modifica compare in più giochi man mano che vengono aggiornati e va contata una volta sola.
  • Deadlock su Steam: in accesso anonimo le sue build non sono visibili; il gioco è coperto dal suo repository, e le nuove build si ricavano dal numero di versione nel file steam.inf dei commit. Valgono 45 punti (sotto la soglia di notifica) perché nelle settimane di aggiornamento ne escono anche 3-5 al giorno.
  • Analisi AI: generata da {{ ai_model }} sui dati raccolti. I fatti rimandano alle prove, le ipotesi sono interpretazioni e possono essere sbagliate.

Dati e citazioni

  • JSON usato dalla ricerca del sito: findings.json.
  • App Android: hlx-watch.apk (apre questo sito; si aggiorna installando l'APK nuovo sopra il vecchio). Ogni 30 minuti circa controlla le ultime scoperte e manda una notifica di sistema per quelle nuove (dalle 23 alle 8 le trattiene e le mostra insieme al mattino).
  • Cronologia HLX: la pagina Cronologia raccoglie gli indizi ad alta rilevanza in ordine di data di prima comparsa, con una spiegazione scritta da {{ ai_model }} una volta per indizio.
  • Riepilogo settimanale: ogni lunedì su Telegram la settimana precedente in breve, con i numeri per gioco e una sintesi scritta da {{ ai_model }}.
  • Notifiche di sistema dal sito: il pulsante Attiva notifiche nell'intestazione (Chrome, Edge e Firefox su PC e Android; su iPhone solo dopo aver aggiunto il sito alla schermata Home). Dalle 23 alle 8 vengono trattenute e arrivano in un solo riassunto al mattino. Arrivano le stesse novità degli avvisi Telegram (punteggio ≥ {{ notify_min_score }}), non i report. Viene salvato solo l'indirizzo anonimo che il browser fornisce per le notifiche, nel bot su Cloudflare; disattivandole dal pulsante viene cancellato.

Per citare una voce, la fonte primaria è il commit di SteamTracking (link "commit" accanto a ogni voce) con file e riga, non questo sito: per esempio SteamTracking/GameTracking-CS2, commit 0214b1f4, DumpSource2/schemas/particles/C_OP_RenderSprites.h:4280.

Le build Steam non hanno un commit: il link "build" apre la pagina SteamDB di quella build, con l'elenco dei depot cambiati; "cronologia" apre lo storico delle informazioni dell'app; "pagina Steam" apre la scheda del negozio. Sono solo link per chi legge: HLX Watch non scarica pagine da SteamDB, legge i dati direttamente da Steam.
