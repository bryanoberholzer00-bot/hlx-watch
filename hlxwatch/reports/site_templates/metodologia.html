Metodologia

In breve

HLX Watch sorveglia dati pubblici dei giochi Valve su Source 2 e registra ogni riga che contiene riferimenti a HLX (il presunto nome in codice di Half-Life 3) o ad altri progetti non annunciati. Ogni voce porta alla sua fonte: il commit di SteamTracking da cui proviene, il file e la riga. Lo strumento non usa account, depot privati né scraping di siti terzi, e non interpreta i dati da solo: le interpretazioni stanno solo nell'analisi AI, separate dai fatti.

Questa pagina è generata dalla stessa configurazione che usa lo strumento, quindi pesi e soglie qui sotto sono quelli realmente applicati. Aggiornata {{ generated }}.

I repository SteamTracking contengono file estratti dai giochi e dump generati da strumenti (stringhe dei binari, schemi del motore, ConVar). HLX Watch è quindi una fonte secondaria: dipende da come SteamTracking estrae i dati, e un cambio di formato dei dump può far "comparire" o "sparire" righe che Valve non ha toccato.

Da dove vengono i dati

HLX Watch non apre i file dei giochi: legge il lavoro di SteamTracking, l'organizzazione di Pavel Djundik (xPaw, autore di SteamDB), che a ogni aggiornamento di un gioco Valve esegue una catena di strumenti open source e pubblica il risultato come testo su GitHub.

  1. SteamFileDownloader scarica dai depot di Steam solo i file che servono, anche singole voci dentro gli archivi VPK.
  2. Source 2 Viewer (ValveResourceFormat) decompila gli archivi in testo: dati di gioco, script, eventi sonori, interfaccia, e l'elenco completo dei file di ogni archivio.
  3. DumpSource2 carica i binari del gioco senza avviarlo ed elenca classi (schemi), variabili, comandi, entità e campi di rete. Gli stessi dati sono consultabili nello Schema Explorer: le voci che vengono da una classe hanno il link "vedi la classe".
  4. DumpStrings estrae le stringhe leggibili dalle DLL e toglie quelle già note; ProtobufDumper ricava i protocolli di rete.
  5. Il risultato è un commit nei repository GameTracking-*; dal 3 ottobre 2026 un'azione con agenti Claude pubblica anche un riassunto di ogni commit, mostrato in pagina iniziale accanto alla build.
  6. HLX Watch legge quei commit e Steam PICS in anonimo, confronta, assegna i punteggi e avvisa.

Gli strumenti di SteamTracking non si aggiornano da soli e la catena dipende da una sola persona: per questo la pagina iniziale mostra lo stato delle fonti.

Cosa HLX Watch non fa

  • Non scarica depot né file dei giochi, e non usa account Steam: legge solo repository pubblici e dati PICS anonimi.
  • Non esegue programmi dentro i giochi (niente iniezioni, debugger o dumper in memoria): nessun rischio di ban VAC.
  • Non fa scraping di SteamDB, che lo vieta; lo cita solo con link per chi legge.
  • Non usa materiale trapelato o ottenuto in modo non autorizzato, come la "Steam2 Teraleak" dell'agosto 2026 o build rubate.
  • Non ripubblica modelli, suoni o immagini dei giochi: riporta righe di testo con il link alla fonte.
  • Non salva né pubblica dati personali: indirizzi email e nomi utente nei percorsi dei file vengono sostituiti da segnaposto prima di entrare nell'archivio.
  • Non annuncia nulla: non usa parole come "leak", "confermato" o "in arrivo" e non deduce date. Una riga nei file è un riferimento, non la prova che un prodotto uscirà, e può anche essere una battuta o un'esca per chi legge i dati.

HLX Watch non è affiliato con Valve. Half-Life, Source e Steam sono marchi di Valve Corporation; i dati citati appartengono ai rispettivi proprietari e sono riportati in forma minima, con il link alla fonte pubblica.

Rimozioni. Se un contenuto non dovrebbe stare qui (dati personali, materiale che non è pubblico, una richiesta del titolare dei diritti), apri una segnalazione su GitHub: viene tolto dal sito e dall'archivio.

Come vengono trovate le voci

  1. Monitoraggio dei commit. Per ogni commit nuovo lo strumento legge la patch di ogni file; se GitHub non la fornisce (file troppo grandi) scarica le due versioni e le confronta. Le righe aggiunte, rimosse o modificate che contengono una parola chiave diventano voci. L'API di GitHub espone al massimo 3000 file per commit: nei commit più grandi gli altri file si leggono direttamente con git.
  2. Scansione completa (ogni {{ full_scan.interval_hours }} ore). L'ultima versione di ogni repository viene scaricata senza storia e cercata per intero, compresi i file che la ricerca di GitHub non indicizza. Prefiltro: {{ full_scan.prefilter }}; soglia {{ full_scan.min_score }} punti. Una riga che cambia solo punteggio, per una modifica alle parole chiave, non conta né come aggiunta né come tolta: conta solo ciò che cambia nei file.
  3. Prima comparsa. Per le voci trovate dalla scansione completa, lo strumento ripercorre la storia del file e cerca per bisezione il primo commit in cui la riga compare.
  4. Steam. Nuove build per branch e app nuove con developer/publisher Valve, nome sospetto o parole chiave.
  5. Struttura dei repository. A ogni run si confrontano gli elenchi delle cartelle sotto game/ e dei file in manifests/ (un file per depot Steam) di ogni gioco, e delle cartelle del repository dei Protobuf (un protocollo di rete per gioco): una voce che prima non c'era diventa una voce structure da {{ structure_score }} punti, anche se nessun file scrive il nome del progetto. Lo stesso per i dump delle DLL in game/bin/win64 e nella cartella del gioco: una DLL nuova è un sottosistema nuovo.
  6. Nodi Pulse. Pulse è lo scripting visuale dei giochi Source 2 recenti; ogni tipo di nodo è una classe CPulseCell_*. Il nodo per le scene recitate "dinamiche" è arrivato in CS2 e Deadlock negli stessi giorni delle fusioni con tracce HLX. Un nodo mai visto è una voce, con più punti per scene, sequenze, dialoghi, telecamera e IA.
  7. Piano annuncio. Un'app Steam nuova di Valve o un repository nuovo di SteamTracking con HLX o Half-Life nel nome diventano un solo avviso "possibile annuncio". Nel repository del gioco le parole HLX non contano (sono ovunque, come Half-Life in quello di Alyx) e l'app viene aggiunta da sola ai giochi seguiti su Steam.
  8. Post ufficiali di Valve. Le altre fonti vedono un annuncio dagli effetti; questa lo vede quando Valve lo pubblica. Un post nella sezione Annunci di Steam che parla di un Half-Life nuovo (HLX, Half-Life 3, "Half-Life: un titolo mai visto") è un possibile annuncio; i titoli già usciti, come Alyx o Episode Two, non contano. Ogni altro post resta in archivio con pochi punti, senza avviso.
  9. Codice pubblico di Valve. Su GitHub Valve pubblica una parte del suo codice (Proton, SteamOS, gamescope, OpenVR, GameNetworkingSockets, gli SDK). Non sono i file dei giochi, ma sono scritti da Valve: un repository nuovo è una voce, e ogni riga dei messaggi dei commit nuovi passa per le stesse parole chiave e per la regola dei post di Steam su un Half-Life nuovo. Provato su un anno di commit (813, in 19 repository): nessuna voce, quindi una che compare è da guardare.
  10. Siti di Valve. Valve protegge i siti di prova di tutti i suoi giochi con un solo certificato HTTPS, rinnovato ogni poche settimane, che elenca ogni dominio (half-life.com, playdeadlock.com, steamdeck.com... 58 a fine ottobre 2026). I certificati sono pubblici nei registri di Certificate Transparency. Un dominio mai visto è probabilmente il sito di un progetto nuovo, preparato prima dell'annuncio: è una voce con avviso, e con HLX o Half-Life 3 nel nome un possibile annuncio. Un sottodominio nuovo di un sito noto resta in archivio. Non si sa se in passato abbia anticipato un annuncio: i registri storici non si possono interrogare in automatico.
  11. Famiglie di classi nuove. Le tracce HLX trovate il 29 ottobre 2026 (aggiunte da Valve il 23 settembre in CS2 e il 7 ottobre in Dota 2) erano una famiglia di nomi C++ comparsi insieme (CHLXCoverPreviewHelper, CHLXBaseProjectileEmitterHelper). Un progetto con un nome in codice nuovo porterebbe una famiglia allo stesso modo, senza la parola HLX. Nella scansione completa giornaliera si leggono i nomi di classe di tutti i giochi (file degli schemi e dump delle stringhe, escluse le librerie di terzi) e la famiglia di ognuno, cioè il primo pezzo dopo la C (CHLX, CCitadel, CMath). Una famiglia mai vista in nessun gioco, con almeno 2 nomi diversi, è una voce. Su CS2, da luglio a ottobre 2026, sarebbero state 4: CHLX e tre famiglie di entità di gioco con API di scripting (CTankTrainAI_API, CMathCounter_API...). Se la famiglia ha una classe sola, contano anche i nomi che iniziano con la stessa parola senza la C: Deadlock è entrato in Dota 2 il 25 marzo 2021 con CCitadelModifierHandleTyped e CitadelHudEvent. Una parola che ricorre in più di 5 nomi (Parse...) è una parola comune e non conta. Una famiglia già segnalata che poi cresce (almeno il doppio dei nomi, e almeno 5 in più) dà un avviso nuovo con 25 punti in più, fino a 95 (sotto l'alta rilevanza"): un progetto vero cresce, il rumore di solito no.
  12. Pulsante 👎 su Telegram. Sotto ogni avviso c'è un pulsante per voce: "è rumore". Le voci nuove dello stesso tipo (gioco, tipo di modifica, parola chiave principale e area dei file) restano in archivio e sul sito ma non mandano più avvisi; ripremere il pulsante annulla. L'elenco dei tipi silenziati è in pagina iniziale. Le tracce HLX forti e i possibili annunci non si possono silenziare.
  13. Cosa cambia in una build. Sotto l'avviso di una build nuova c'è una riga che dice che cosa è cambiato, ricavata dal commit di SteamTracking della stessa build: solo traduzioni o testi nuovi in inglese, file del gioco nuovi (con il nome), tolti o modificati, programmi, messaggi di rete, numero di versione, e se nello stesso commit ci sono righe da avviso. Si aggiungono le ultime note ufficiali di Valve su Steam degli ultimi 14 giorni. Se il commit arriva dopo l'avviso, la spiegazione arriva in un messaggio breve al giro successivo (si aspetta al massimo un giorno).
  14. Registri dei domini. playdeadlock.com è stato registrato il 5 aprile 2024, più di quattro mesi prima dell'annuncio di Deadlock, con gli stessi server DNS di half-life.com. Ogni giorno si legge con RDAP (il servizio pubblico dei registri) chi gestisce nomi come half-life3.com (registrato dal 1999 presso lo stesso registrar di playdeadlock.com, ma parcheggiato), halflife3.com, hlx.com: se uno passa ai server DNS di Valve è un segnale forte, un cambio di registrar una voce con avviso. Dalla lista gratuita dei domini registrati il giorno prima si controllano quelli con Half-Life, HLX o la forma playnome.com (come playdeadlock.com, playartifact.com): solo quelli con i DNS o il registrar di Valve diventano voci. La lista gratuita è parziale.
  15. Hardware Valve in SDL e Linux. Perché un controller funzioni su PC, il suo identificativo USB va aggiunto alla libreria SDL e al kernel Linux, spesso con il nome in codice (oggi Ibex, Proteus, Nereid). Un nome mai visto è una voce; se il nome in codice compariva già altrove (altri nomi, archivio, altri file del repository) la voce lo dice e vale meno.
  16. Pacchetti di SteamOS. L'archivio pubblico dei pacchetti di Steam Deck e Steam Machine (steamdeck-packages.steamos.cloud), elenchi jupiter-main e holo-main, ogni 12 ore: un pacchetto di supporto per un dispositivo con un nome in codice mai visto (come fremont-hw-support per la Steam Machine), una famiglia di archivi nuova o una versione nuova di SteamOS.
  17. Certificazioni FCC. L'elenco dei dispositivi radio registrati da Valve (richiedente 2AES4), letto da fccid.io ogni 12 ore perché il sito ufficiale della FCC respinge i programmi. Si salvano solo codice, data e descrizione. Geekbench è stato scartato: risponde con un controllo anti-robot.
  18. Documentazione di Steamworks. Le pagine pubbliche per gli sviluppatori (partner.steamgames.com/doc), ogni 12 ore: l'indice completo (una pagina nuova, soprattutto nella sezione Steam Hardware, dove ogni dispositivo ha le sue) e il testo della pagina Steam Hardware, dove Valve elenca i suoi dispositivi. Il pacchetto dell'SDK e il suo registro delle modifiche richiedono l'accesso da sviluppatore e non si leggono.
  19. Obiettivi di Steam. L'API pubblica di Steam elenca i nomi interni degli obiettivi di un gioco: un aggiornamento che ne aggiunge li mostra, a volte prima delle note. Per le app riservate, come Deadlock o le app private di Valve, Steam risponde vuoto e non si forza niente; se un'app passa da nascosta a visibile (come per l'errore di Valve di settembre 2026) è una voce a parte.
  20. App Steam nel codice di Proton. Proton elenca le app che ricevono una correzione dedicata (circa 45 nuove all'anno). A ogni aggiornamento del file, ogni numero nuovo si controlla sul negozio Steam: un'app non ancora pubblica o di Valve è una voce con avviso; un gioco già in vendita di un altro editore resta in archivio.
  21. Controllo veloce dell'annuncio. GitHub avvia i run in modo irregolare, anche ogni 4-5 ore. Per questo il bot su Cloudflare, che gira puntuale, guarda ogni 10 minuti le due fonti che possono annunciare un gioco: i post ufficiali di Steam e i repository nuovi di SteamTracking e di ValveSoftware, con le stesse regole. Se trova un Half-Life nuovo avvisa subito su Telegram, nelle notifiche del sito e nell'app Android; il run completo su GitHub poi lo archivia con i dettagli. Se il controllo veloce non riesce da più di 2 ore, il proprietario riceve un avviso; l'ora dell'ultimo giro riuscito è nello stato delle fonti, in pagina iniziale.
  22. Il contatore di Valve. Ogni build di CS2, Dota 2 e Deadlock scrive nel file pubblico steam.inf il numero della modifica di Perforce da cui è stata compilata (SourceRevision) e l'ora della compilazione. Il numero è unico per tutta Valve, quindi la sua crescita misura quante modifiche salva l'azienda ogni giorno. Lo storico dal 2016 è stato ricostruito da tutti i commit dei steam.inf (4.964 build); a ogni giro si leggono i tre file di oggi. Il ritmo degli ultimi 60 giorni si confronta con i 12 mesi prima: sopra del 30% è un'ondata e parte un avviso, una volta sola. Le fasce orarie separano le persone dai programmi automatici, e gli aggiornamenti pubblici dei progetti noti (commit di SteamTracking, una volta al giorno) mostrano quanta parte del lavoro si vede. La prova delle feste confronta ogni anno la settimana del Ringraziamento e il Natale con le tre settimane prima: a Natale Valve di solito va al 13-25% del ritmo normale, anche nel 2019 prima di Alyx. Alla fine di ogni festa parte un messaggio con il risultato.
  23. Una scheda per ogni traccia. Ogni traccia del registro degli esiti ha la sua pagina: tipo, esito, giochi e date, ogni comparsa nell'archivio con il link al commit, le altre tracce comparse lo stesso giorno nello stesso file e le righe vicine, cioè le righe attorno alla traccia quando è comparsa. Le righe vicine vengono dal diff del commit; per le tracce trovate dall'archeologia, che non hanno il diff, il file viene scaricato una volta sola da raw.githubusercontent.com a quel commit. Nei dump di stringhe le righe vicine non dicono niente, perché quei file sono in ordine alfabetico, e la scheda lo avverte. Una prova su tutto l'archivio ha mostrato che i nomi vicini sono quasi sempre nomi generici del motore, presenti anche altrove: per questo non diventano avvisi.
  24. Controllo automatico del sito. Dopo ogni aggiornamento, prima di pubblicarlo, il sito generato viene controllato: i file che servono ci sono, i dati dell'app Android si leggono, ogni pagina è completa e senza valori mancanti, i link interni portano a pagine e sezioni che esistono, e il termometro ha lo stesso valore sulle pagine e nel widget. Se manca un file o una pagina è tagliata, il sito non viene pubblicato e resta online la versione precedente; gli altri problemi vengono solo segnalati. Il proprietario riceve un avviso su Telegram quando compare un problema nuovo e quando tutto torna a posto. L'esito dell'ultimo controllo è nello stato delle fonti, in pagina iniziale.
  25. Riassunti di SteamTracking. Dal 4 ottobre 2026 SteamTracking fa leggere ogni aggiornamento a una squadra di agenti Claude e pubblica un riassunto come commento sul commit. La pagina iniziale lo mostra accanto alla build; una riga che parla di HLX, o che sta nella sezione sugli altri giochi e progetti non annunciati, diventa una voce con avviso.
  26. Rinomine. Valve non toglie la tecnologia nata per HLX: la rinomina. Quando in un commit una riga con HLX sparisce e ricompare nello stesso file con un altro prefisso (hlx.hrtf_basic diventato core.hrtf_basic il 21 gennaio 2026), la voce dice dove è finita: nel motore comune, in un gioco come Deadlock (citadel) o senza prefisso. Dei sette nomi HLX tolti dal 2021, cinque esistono ancora con un altro nome.
  27. Hardware Valve. Come i data miner di SteamVR: ogni visore o controller dichiara il suo nome nel campo controller_type dei profili, e un nome mai visto è una voce. Manifesti, impostazioni, firmware e profili dei driver Valve sono file sorvegliati; i nomi in codice Deckard, Fremont, Ibex, Galileo, Neptune e Roy sono parole chiave.
  28. Entità senza padrone. Le definizioni delle entità per l'editor (game/core/*.fgd) arrivano in ogni gioco; le classi C++ che le implementano solo nel gioco che le usa. Alla scansione completa giornaliera si confrontano tutti i giochi insieme: un'entità che nessun gioco implementa, o un helper di Hammer mai visto, appartiene a un altro progetto. Hammer stesso fa questo controllo. Le FGD condivise dei nemici sono anche file sorvegliati: CS2 e Dota 2 non hanno nemici, ma quei file cambiano proprio nelle date delle tracce HLX.
  29. Famiglie di token di localizzazione. Ogni testo a schermo è un token "Famiglia_Nome" nei file *_english.txt (CSGO_, DOTA_, Citadel_, HLVR_): è il posto in cui Valve è obbligata a scrivere il nome del progetto. Le famiglie presenti vengono imparate alla prima scansione completa; poi un file di localizzazione nuovo vale {{ loc.score_new_file }} punti e una famiglia mai vista con almeno {{ loc.min_tokens }} testi in un commit {{ loc.score_new_prefix }} (Deadlock meno: ogni eroe nuovo porta la sua famiglia).

Nomi di progetto nuovi e file sorvegliati

Le parole chiave trovano solo nomi già noti. Per accorgersi di un progetto con un nome diverso, HLX Watch guarda i posti in cui Valve scrive i nomi in codice: le espressioni mod != nome degli strumenti, prodotti e componenti del bug reporter, le cartelle source2/main/content/nome e i rami di compilazione che restano nei binari (C:\buildworker\csgo_rel_win64\...: il ramo che ha prodotto la DLL), e il messaggio di rete con i comandi del giocatore che ogni gioco definisce (CDota2UserCmdPB, CCitadelUserCmdPB per Deadlock; in Dota 2 dal giugno 2022 al marzo 2023 c'era CHLXUserCmdPB). Un nome che non è tra quelli noti diventa una voce "codename" da {{ codename_score }} punti. Nomi noti finora: {{ project_names|join(", ") }}.

Per l'hardware ci sono due posti in più, da 80 punti (avviso, ma non alta rilevanza): l'elenco dei dispositivi Valve nei driver di SteamVR, una riga per prodotto (Valve Index HMD; il 31 marzo 2022 ci è entrato Valve Deckard, il futuro Steam Frame) e i tipi di controller del client di Steam (k_EControllerType_SteamControllerNeptune, comparso l'11 maggio 2021, due mesi prima dello Steam Deck). I tipi di controller di altre marche valgono 60 punti. Tutti e due vengono dalla prova sul passato. Quando in un file compaiono insieme 4 o più nomi nuovi (un elenco intero, come i tipi di controller nel maggio 2021) arriva un avviso solo con tutti i nomi, invece di uno per nome.

Filtri contro i falsi positivi

  • Righe che contengono {{ global_excludes|join(', ') }} (nome in codice di Deadlock) scartate, salvo match ad alta rilevanza.
  • Corrispondenze con maiuscole miste (hLX, HLx): sequenze casuali nei dump binari, scartate.

  • Nuova: la stringa (o il suo identificatore) non era mai stata vista prima nell'archivio.
  • + altri N file: la stessa riga è cambiata in più file dello stesso commit (tipico dei dump di più eseguibili): conta come un'unica modifica. + altre N righe nello stesso file: la stessa stringa compare in più punti dello stesso file (per esempio una classe ripetuta nel dump di un eseguibile).
  • Data delle voci della scansione completa: quando la prima comparsa è nota, la data della modifica è quella del primo commit in cui la riga compare, non quella della scansione che l'ha trovata.

Tipo di prova

Ogni voce mostra il tipo di prova, con la stessa gerarchia che SteamTracking usa per i suoi riassunti, dalla più forte alla più debole:

  1. dati di gioco o traduzioni: file che il gioco usa davvero (definizioni, testi a schermo);
  2. classi, variabili o protocolli del motore: schemi, convar, entità, messaggi di rete;
  3. elenco di file: il file esiste nell'archivio del gioco, ma il suo contenuto non si vede;
  4. solo stringhe dei binari: testo trovato dentro una DLL; da solo dice soltanto che le stringhe suggeriscono qualcosa.

"Mai vista prima" significa che la riga non era mai comparsa nell'archivio, che con l'archeologia parte dal 2016. Il punteggio misura quanto una riga interessa la ricerca su HLX, non quanto è forte la prova.

Fusione del motore ed esiti

Quando la stessa riga compare in CS2, Dota 2 e Deadlock entro 60 giorni, la voce lo dice: "fusione del motore". Valve porta periodicamente il ramo principale di Source 2 in tutti i giochi, quindi quella riga viaggia con il codice condiviso e non indica lavoro nuovo sul gioco in cui compare. La pagina Esiti segue ogni traccia HLX fino al suo esito: ancora presente, rinominata (e dove è finita), sparita.

Il contrario è "solo in" un gioco: una riga nelle parti che i tre giochi condividono (stringhe dei programmi del motore, classi, variabili e protocolli) che gli altri due non hanno mai avuto, né nell'archivio né al primo giro. È lavoro su quel gioco, non codice comune in viaggio. Non si segnano le righe con il nome del gioco stesso (C_DOTA_..., citadel_...), ovvie, e il segno si ricalcola a ogni giro: se la riga arriva più tardi anche negli altri giochi, diventa una fusione del motore. Nella Ricerca c'è il filtro "Solo in un gioco".

Errori corretti e revisione settimanale

HLX Watch sbaglia, e gli errori si correggono in due modi. Ogni errore corretto diventa un esempio con il risultato giusto (il tipo di una traccia, le parole chiave di una riga, la spiegazione di una build, un esito, un avviso da non mandare). A ogni aggiornamento tutti gli esempi si ricontrollano con le regole di quel momento: se una modifica fa tornare un errore già corretto, il proprietario riceve un avviso e lo stato delle fonti in pagina iniziale lo mostra.

Ogni lunedì, dopo il riepilogo, una revisione con l'AI riguarda gli avvisi della settimana e le voci segnate con 👎, con le prove (la riga, il contesto, se il nome esisteva in Alyx, in quali altri giochi c'è la stessa riga), e propone al massimo tre correzioni, ognuna con il perché. Sono possibili solo tre correzioni: il tipo di una traccia, una nota nella pagina Esiti, oppure niente più avvisi per un tipo di voce di rumore. Le tracce HLX forti e i possibili annunci non si possono mai silenziare. Nessuna correzione si applica da sola: arriva su Telegram con i pulsanti ✅ Applica e ❌ No, e quella approvata entra nell'elenco qui sotto.

Confronti, tipi di traccia e grafici

Confronto con Alyx e con gli altri progetti Valve (pagina HLX e Alyx a confronto). Una volta sola, un workflow su GitHub ha clonato gli archivi SteamTracking dal 2013 e dal 2016 e ha cercato con git log -G la prima comparsa di ogni nome con un nome in codice: hlvr (Half-Life: Alyx) fino alla sua uscita, citadel (Deadlock), csgo nel motore Source 2 (Counter-Strike 2), neptune e steampal (Steam Deck), deckard (Steam Frame), ognuno fino al giorno dell'annuncio. È storia chiusa: i risultati sono salvati nel repository (alyx_seed.json, progetti_seed.json) e non si ricalcolano. I falsi positivi sono stati tolti controllando i nomi a mano, con regole scritte nel codice e riportate nella pagina (per esempio i nomi con "alyx" di Half-Life 2 Episodio 2, o le mappe d3_citadel di Half-Life 2). Si contano solo nomi diversi, alla prima comparsa; una data che coincide con l'inizio dell'archivio vale "almeno".

Motore o gioco. Ogni traccia HLX viene classificata in base a parole chiave del suo nome: gioco (armi, munizioni, oggetti, nemici e il loro comportamento, elementi come il thumper o le barriere dei Combine), motore (materiali, particelle, suono, fisica, impostazioni degli shader come mod != hlx), strumenti di lavoro (il configuratore dei bug) o da capire. Lo stesso pezzo scritto in modi diversi conta una volta: per questo le tracce dell'archivio sono più dei pezzi contati. Le regole sono state controllate a mano su tutte le tracce di HLX e sui nomi di Alyx; una traccia che non corrisponde a nessuna regola resta "da capire", senza indovinare.

Negli avvisi le tracce HLX portano lo stesso tipo: 🎮 pezzo di gioco, ⚙️ pezzo di motore, 🔁 eredità di Alyx (un nome hlvr di Alyx ricomparso con hlx). Se il tipo non è chiaro l'avviso non ne mostra nessuno.

Il grafico giorno per giorno della pagina iniziale ha una colonna per ogni giorno. L'altezza conta le voci da 50 punti in su; le altre stanno in una fascia grigia sotto la linea, in scala ridotta. I contenuti già presenti non contano, e le voci trovate dalla scansione completa prendono la data della loro prima comparsa, come nell'elenco. Un giorno che stacca tutti gli altri esce dal grafico con il suo numero, invece di schiacciarli.

Nessuno di questi confronti prevede un annuncio: tra i progetti Valve passati non c'è un segnale che si ripeta prima dell'annuncio, e la pagina di confronto lo mostra.

Prova generale dell'annuncio

Un avviso che serve una volta sola va provato prima. La prova generale manda un finto "possibile annuncio", con scritto chiaramente PROVA GENERALE, su Telegram, nelle notifiche del sito e nell'app Android, anche nell'orario di silenzio. Non entra nell'archivio: resta per 12 ore in bot/ultime.json, il tempo perché l'app la legga. La lancia a mano chi gestisce HLX Watch, dal workflow su GitHub (opzione "Prova generale dell'annuncio") o con python -m hlxwatch prova-annuncio. La data dell'ultima prova è nello stato delle fonti, in pagina iniziale.

Se ricevi questa notifica: Valve non ha annunciato niente, è solo un controllo che la catena funziona.

Dati aperti

Tutti i dati di HLX Watch sono pubblici e si possono riusare citando HLX Watch e le fonti (SteamTracking, Steam):

  • feed.xml: feed Atom delle voci da 100 punti, per un lettore di feed;
  • findings.json: le voci mostrate dalla Ricerca;
  • bot/ultime.json e bot/indice.json: le ultime novità e l'indice usati dal bot e dall'app;
  • bot/termometro.json: il termometro HLX del widget dell'app Android, un indice da 0 a 100 delle tracce HLX forti recenti (per data del commit; il peso di una traccia dimezza ogni settimana), con l'ultima traccia e l'ultima voce; 100 solo per un possibile annuncio o durante la prova generale;
  • fast/annuncio.json: i possibili annunci trovati dal controllo veloce negli ultimi 3 giorni (di solito vuoto);
  • nel ramo data del repository: findings.csv (tutte le voci), hlxwatch.sqlite.gz (l'archivio completo, SQLite) e stats.json, aggiornati a ogni run;
  • nella release archivio: una copia dell'archivio per settimana, le ultime 8.

Prima di salvare, ogni run controlla che l'archivio non si sia svuotato: se voci, build o stringhe viste calano più del 5% rispetto all'ultimo salvataggio, il run non salva niente, avvisa, e il run dopo riparte dall'ultima copia buona.

Limiti noti

  • Ritardo: i run pianificati su GitHub partono in modo irregolare (a fine ottobre 2026 in media ogni 4-5 ore). Per questo il bot su Cloudflare avvia lui un run quando sono passati 30 minuti dall'ultimo, con un token GitHub che può solo avviare i run di questo repository; se il token manca o scade restano i run pianificati, e la pagina iniziale lo dice. Una scoperta arriva quindi entro mezz'ora circa dal commit di SteamTracking. Un possibile annuncio anche prima: lo cerca il controllo veloce, ogni 10 minuti.
  • Parole chiave: si trova solo ciò che corrisponde all'elenco qui sopra. Un progetto con un nome in codice nuovo passa inosservato finché non viene aggiunto.
  • Formato dei dump: SteamTracking cambia talvolta come estrae i dati (per esempio dal 13 ottobre 2026 molte stringhe già note sono filtrate dai dump dei binari). Spostamenti tra file non sono modifiche di Valve.
  • Codice condiviso: Source 2 è un motore comune; la stessa modifica compare in più giochi man mano che vengono aggiornati e va contata una volta sola.
  • Deadlock su Steam: in accesso anonimo le sue build non sono visibili; il gioco è coperto dal suo repository, e le nuove build si ricavano dal numero di versione nel file steam.inf dei commit. Valgono 45 punti (sotto la soglia di notifica) perché nelle settimane di aggiornamento ne escono anche 3-5 al giorno.
  • Analisi AI: generata da {{ ai_model }} sui dati raccolti. I fatti rimandano alle prove, le ipotesi sono interpretazioni e possono essere sbagliate.
